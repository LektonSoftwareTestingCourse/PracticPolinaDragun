## 1. Область тестирования и подход
Объектом верификации является распределенная микросервисная система массового процессинга СМП.

В область детального тестирования входит ядро системы: сервис авторизации (Authorization Service) и сервис управления картами (Card Management Service).
Инфраструктурные элементы (gateway service и switch) и аналитический слой (transaction logger и дашборд) проверяются на уровне корректности маршрутизации трафика, соблюдения структуры данных и сквозного прохождения сообщений.

Подход включает глубокое тестирование методом черного ящика для сервисов ядра и высокоуровневые проверки периферийного слоя. 

В качестве основных техник тест-дизайна для ядра используются классы эквивалентности, анализ граничных значений и попарное тестирование. Для периферии и инфраструктуры применяются чек-листы критического пути и дымовые проверки связности.

## 2. Критерии входа и выхода

- Критерии входа:
    - Развернута инфраструктура стенда, все контейнеры запущены
    - пройдены базовые хелсчеки 
    - база данных инициализирована схемами целевых таблиц, первоначальные миграции пройдены
    - зафиксированы спецификации описывающие сетевые контракты взаимодействия
    - готов тестовый набор данных

- Критерии выхода:
    - Успешно выполнены и зафиксированы все спроектированные тесткейсы
    - Чек-листы дымового тестирования инфраструктуры и верификации критических путей полностью пройдены 
    - Достигнуты цели обеспечения качества процессинга: подтверждено прохождение сквозной цепочки, точность деклин-кодов, финансовая точность списаний и пополнений, корректность отсечения невалидных пакетов шлюзом.

## 3. Критерии приостановки и возобновления

- Критерии приостановки тестирования:
    - Полная или частичная недоступность точки входа или маршрутизатора, приводящая к сетевым таймаутам или системным ошибкам при попытке отправить любую транзакцию.
    - Сбои на уровне субд или брокера
    - Обнаружение критического несоответствия развернутой реализации утвержденным сетевым контрактам 

- Критерии возобновления тестирования:
    - Развертывание исправленной сборки микросервисов, устраняющей блокирующие дефекты
    - Прохождение одной эталонной транзакции критического пути с получением корректного кода ответа.

## 4. Ресурсы, расписание, риски и метрики
Человеческий ресурс составляет 1го тестировщика

Инструменты: PICT для попарного набор; JUnit 5 + Mockito + AssertJ на модульные тесты на Java; Spring Boot Test, Testcontainers, WireMock, REST Assured на API и интеграция; Docker Compose на тестовое окружение; Swagger UI / Postman для ручных проверок.

Расписание в соответсвиями с проходными практиками курса.

**Риски**

Если Bin Lookup Service перестанет отвечать, Authorization по ТЗ не отклоняет транзакцию, а берёт issuerId
из таблицы BIN Switch. Снаружи такая авторизация выглядит успешной, поэтому дефект основного пути обогащения может остаться незамеченным


По tz/04 операция «проверить баланс и зарезервировать» не атомарна: между запросом карты и резервированием 
другая транзакция может изменить баланс. При параллельных проверках баланса это даёт нестабильные результаты.

Без ограничений генератор строит комбинации, которые по алгоритму авторизации ничего не проверяют например
сумма ровно на границе лимита у заблокированной карты, хотя до проверки лимитов дело не доходит. 


**Метрики**

Каждая строка набора должна быть спроецирована
ровно в один тест-кейс. Целевое значение 100%

Каждый класс из таблицы классов должен иметь хотя бы один тест-кейс — либо через строку попарного набора, либо отдельный.
целевое значение  100%.

Для каждой границы проверяются три точки: ниже, на границе и выше. Целевое значение 100%.

Для каждого кода и причины отказа, перечисленных в ТЗ должен существовать хотя бы один тест-кейс, в котором этот код
проверяется в ожидаемом результате. Целевое значение  все коды.
